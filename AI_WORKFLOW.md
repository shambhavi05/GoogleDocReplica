# AI Workflow

How this got built, what AI did, what broke, what I had to catch.

## Tools

Claude Code (Claude Sonnet 5) — did the whole thing. Planning, writing backend and frontend code,
running builds and tests, and actually driving a real browser to click through the app as each
demo user and check things worked, not just trusting the code looked right.

## Where it actually helped

- Scaffolded the whole Maven + Vite/React/Tailwind setup in minutes instead of me hand-wiring
  build config.
- Wrote entities, repos, migrations, security config, service-layer auth, and controllers as one
  coherent pass — not disconnected snippets, each piece built with the others in mind.
- Wrote the React pages wired to real API calls from the first draft. No mock data to rip out
  later.
- Wrote the JUnit/Mockito and Vitest test suites in one go.
- Actually logged in as each demo user in a real browser and clicked through login → dashboard →
  editor → share → logout, which caught bugs that just reading the code wouldn't have.

## What the initial prompt was

One detailed assignment brief — product requirements, stack, project layout, what security/
testing/deployment should look like, plus explicit rules like "don't claim something works without
testing it" and "no TODOs on required features." One clarifying question up front (how auth should
work, since "lightweight" wasn't specific enough), then it just built from there.

## Bugs found by actually running the thing, not just reading code

1. **`@Lob` on the content field broke the version column.** First cut of the Document entity had
   `content` annotated `@Lob`. First real request against real Postgres threw
   `DataIntegrityViolationException: Bad value for type long` — Hibernate's LOB handling was
   stepping on the adjacent `@Version` field. Fixed by dropping `@Lob`, just a plain
   `@Column(columnDefinition = "TEXT")` — fine for a field that's always read/written whole.

2. **CSRF silently blocked every save.** Initial security config had a cookie-based CSRF repo
   wired up. Every PUT/POST/DELETE after login came back 403 because the frontend never read the
   token back. Turned CSRF off for `/api/**` instead of adding token plumbing for no real security
   gain here — documented as a trade-off in ARCHITECTURE.md.

3. **TipTap fired autosave on page load for viewers.** Loading a document called
   `editor.commands.setContent()`, which triggered `onUpdate`, which tried to save — even for a
   Viewer who hadn't typed anything. Showed up as an error banner the second Charlie opened a doc.
   Fixed with `emitUpdate: false` on the initial load plus a ready-flag that blocks saves until the
   doc and the user's role are both confirmed.

4. **CORS didn't allow PATCH.** Added later, when building comment-resolve. The allowed-methods
   list only had GET/POST/PUT/DELETE/OPTIONS from the original build. First click of "resolve" in
   the browser got a 403 on the preflight. One-line fix, added PATCH.

5. **PDF export crashed on the first real run.** `openhtmltopdf` parses HTML with a strict XML
   parser, not an HTML5 one. First version emitted `<meta charset="utf-8">` without closing it —
   valid HTML, invalid XML — which threw immediately. An automated test caught this before it ever
   hit the browser. Fixed by emitting actual well-formed XHTML.

6. **DOCX bullet lists from some tools didn't import as lists.** Parser originally only checked
   Word's numbering ID to detect list items. A `.docx` built with python-docx sets the paragraph
   *style* to "List Bullet" without setting a numbering ID, so those came through as plain text.
   Caught by actually importing a generated test file and checking the response, not by reading
   the parser. Fixed by also checking for a "List"-named style.

Smaller stuff caught the same way: duplicate TipTap Underline extension registration (removed), a
stale frontend test that broke after a dev-mode auto-login tweak (fixed the test, not the app
behavior, since that tweak was intentional).

One non-bug but worth noting: partway through, two completely separate local projects on this
machine turned out to be sharing the same Postgres port, and the other one ran with
`ddl-auto=create-drop` — meaning every time *that* backend restarted, it quietly wiped this
project's database. Found by checking `ps aux` for the actual competing process. Fixed by moving
this project onto its own isolated port rather than touching the other project.

## How all of this got checked

- **Backend**: `mvn test` after every real change. Started at 17 tests, ended at 26 — added
  coverage for DOCX parsing (built against a real in-memory `.docx`, not a fixture file), comment
  permissions (viewer-can-comment, author-can-resolve-own, non-author-can't-touch-others, owner-
  can-override), and export (actual Markdown string checks, actual PDF-magic-number check on the
  generated bytes).
- **Every endpoint, every permission combo**: hit directly with curl against a real Postgres
  instance. Not just the happy path — unauthenticated 401s, wrong-role 403s, no-access 404s,
  duplicate-share 400s, stale-version 409s, bad-file-upload rejections. All actually fired and
  actually checked, not assumed from the code.
- **Frontend**: `tsc -b && vite build` after every change, plus the Vitest suite.
- **End to end, through the real app**: logged in as all three demo users, created/edited/
  autosaved documents, confirmed saves actually hit Postgres by reloading, shared and revoked
  access while watching the network tab (not just the resulting screen), confirmed Charlie's
  editor genuinely can't be typed into (not just visually disabled), confirmed Docker Compose
  builds and boots the whole stack, tested presence with two real logged-in sessions seeing each
  other, downloaded both export formats and opened the actual files.

Nothing claimed here that wasn't actually run and checked. If something's marked incomplete in
SUBMISSION.md, it's because it genuinely isn't done — not because it was skipped in the writeup.
